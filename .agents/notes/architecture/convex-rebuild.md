# Convex control-plane rebuild

> Status: proposed implementation plan for [#353](https://github.com/zevium-dev/core/issues/353), not authorization of unresolved product policy. Updated: 2026-10-10.
> Baseline: `120b9cf` on `origin/develop`, after #383 migration deletion, #374 key ownership fix, #381 MCP billing fix, #372 capability design and #388 key index correction. #376 gateway pruning is still open at inspection; its receiver/ControlDO deletion is an implementation prerequisite, not current `develop` behavior. Fresh deployment; no customer-data migration. This PR changes documentation only.

Build a replacement behind the existing web function names, then switch web, gateway, and provider destinations to one fresh deployment. Preserve the accounting and authorization contracts, replace funding lineage with payment-bound lots, and remove the unused registry outbox after moving its two live responsibilities. Use seven implementation PRs, with independent feature and wallet work after the foundation.

The [audit](../findings/codebase-audit-convex.md) is the starting point, not a current inventory: #383 removed 14 tables, while some things marked unused still have callers. In particular, both import limiters run, moderation history has a UI mode, and user mirrors supply billing member labels. Release accounting remains only as an unused export/HTTP route after tooling pruning. The target below is **32 application tables**, including two future-rail tables. This is an explicit deviation from the issue's approximate 24: its own audit sketch groups multiple physical tables in single rows. Deleting durable adjustment state, searchable tag rows, or moderation history to meet a count would lose required behavior. Component-owned rate-limiter tables are additional and must be reported separately in PR 1.

## 1. Current surface contract

Inventory method: read `convex/schema.ts`, `http.ts`, registered exports in every current module, and direct `api.module.function` plus string `makeFunctionReference` callers in `apps/web/src` and `apps/gateway/src`; exclude tests and incidental URLs. **81 distinct function names** below. Gateway also calls three HTTP routes. Internal functions are implementation details except the deployed-key `wallets:recordUsage` fallback. Provider routes and now-unused release tooling APIs are listed separately.

Notation: `?` means optional; `Id<T>` is the generated Convex ID type, not an arbitrary client-selected tenant. `paginationOptsValidator` means `{numItems,cursor:string|null}` plus Convex's optional pagination controls. `Page<T>` means `{page:T[],isDone,continueCursor}` with optional framework split/status fields preserved. The source validators still own exact bounds and error behavior. `orgSlug` is a navigation consistency check; authorization derives the active org from the signed JWT.

DTO abbreviations:

- `Project`, `Organization`, `User`, `Review`, `SpecVersion`, and `RotationOperation` currently expose source documents. Preserve consumed fields; replace document returns with explicit DTOs before embedding secrets in a target row. Never spread target `projects` or `organizations` into a response.
- `KeySettingView`: `_id,keyId,keyFamilyId,keyName?,ownerUserId?,budgetId?,budgetRevision?,monthlyCapCredits?,disabled,rotatedFromKeyId?,graceUntil?,rotationRequiredAt?,lifecycle?,createdAt,updatedAt`. No raw key or hash. Boundary validators are `verifiedKeyProjectionValidator` / `verifiedKeyRotationProjectionValidator` in `convex/keySettings.ts`, with shared signature/semantic verification; keep their full signatures and expiry/identity checks.
- `PublicListing`: listing name/slug/description/tags, publisher name/handle, publication time, pricing/free-tier summary, endpoint count, quality. `PublicReview`: `id,rating,body,createdAt,updatedAt,reviewerLabel,response:{body,updatedAt}|null`.
- `UsageListItem`: `eventId,projectRef,projectName,projectSlug,endpoint,method,credits,status,latencyMs,keyId,memberId?,memberName?,at`. Preserve member redaction from `usageView`.
- `WebhookEndpointMetadata`: `url,active,secretVersion,createdAt`. `OrgAccess` is the shared role/capability DTO. `getPayoutState` totals retain pending/available/allocated/paid/reversed/failed values; aggregation must not change with the recent-rows limit.

## 2. Target schema

All rows get Convex `_id` and `_creationTime`. Unless marked `?`, fields are required. Times are UTC epoch milliseconds; `day` is UTC date and money uses safe integers. An optional field exists only for a product state (not a migration stage). Discriminated unions require their variant's fields. Enumerated state names below are implementation proposals, with validators frozen in PR 1.

Index notation `name(fields) → query` specifies both ordering and the named consumer. “Unique” means an indexed absence/read check and write in the **same mutation**; a Convex index does not impose a SQL uniqueness constraint. Scope every ID lookup with authenticated ownership before returning it. [Convex index documentation](https://docs.convex.dev/database/reading-data/indexes/) describes range ordering; test concurrent insertion rather than assuming `.unique()` enforces uniqueness.

## 3. Money core: small transactions, explicit edge authority

### Size and module boundary

Target **~2,000 non-test lines for ledger/lot/settlement policy**, not for all Stripe HTTP, crypto, tenancy, DTOs, and recovery transport. Proposed allocation: `money/walletLedger.ts` 180, `money/lots.ts` 300, `money/settle.ts` 420, `money/adjustments.ts` 420, `money/publisherLedger.ts` 260, `money/transfers.ts` 240, `accounting.ts` 100, plus ~80 shared types. Measure in PR 4. This is a sizing target, never justification to drop crash recovery or business invariants. Stripe orchestration stays in `billing.ts`, `payouts.ts`, and small provider actions; each DB mutation completes one bounded state transition.

There is one serialized edge wallet per `ownerKey` and one authoritative Convex ledger per wallet. Per-request admission stays in the wallet DO. Convex batches wallet writes; the mandated sharded rate-limiter component protects contended admission to paid search/import/report actions, **not** the money ledger. Neither a rate limiter nor eventual aggregation can replace atomic ledger accounting. Update dashboard/earnings rollup deltas in the accepted settlement transaction, once per ref; release/reversal transactions also update their financial rollup deltas. Background recomputation is a bounded audit, not a second eventually consistent money source.

### Wallet invariant and funding lots

For every committed wallet transaction:

1. `balance = sum(walletEntries.amount) >= 0`; `sequence` is contiguous and each entry's `balanceAfter` is exact. Only `appendWalletEntry` changes balance. Same ref + identical immutable facts is a no-op; same ref + changed facts fails before any write.
2. `balance = sum(lot.remainingCredits)` and each lot satisfies `granted = remaining + consumed + reversed + expired`. Restoration moves credits from the reversed bucket back to remaining in the **same original lot**, preserving its payment identity and expiry; no new source masquerading as a new top-up. Restore to expired inventory if its original expiry has passed.
3. `promoCredits` equals remaining nonrefundable promotional inventory. Consume promo first, then refundable lots FIFO by creation time and ID. Positive admin credits also have explicit lots; negative adjustment uses the same allocator and freeze protocol.
4. Every settled debit has exact source slices and a usage row; every paid source slice yields exact `publisherEarningSplit`. Zero balance denies even explicit-zero-price/free-tier execution; keyless mock remains the stated non-executing exception.
5. All money/sequence/token inputs are bounded safe integers. Credits use 10,000 per USD; accounting atoms use 10,000 per credit. No floating-point dollars in a ledger mutation.

Lot fragmentation must not become a post-execution rejection. The v2 background checkpoint carries available lot IDs, amounts, priorities, and expiry times into the single DO. Its reservation selects at most **32 source slices** and marks them held durably before dispatch. A request needing more slices fails **before upstream** with a recoverable funding-capacity error; advertise this proposed bound to the owner. Checkpoints themselves are paged at a pinned wallet sequence and installed atomically. Do not compact away payment identity. If realistic workloads hit the 32-slice bound, raise it within measured transaction budgets or design resumable funding allocation before enabling those workloads.

Convex validates slices against the locked wallet epoch, then atomically appends debit, updates lots, inserts immutable usage and increments sharded source earning buckets. Budget the **one-event worst case**, then group events within the measured transaction write/byte limit; keep the 100-event wire cap. A large batch may get retryable unprocessed refs, but a valid admitted single event always fits and progresses. This removes B8's fixed budget that repeatedly rejects almost every event. Store lot slices once on usage; no compaction components, funding-state mirror, lineage journal or allocation-rollup mirror.

### Fix #357 with a freeze/drain barrier

A newer balance alone is not enough to reconcile two authorities. Recommended v2 extension: epochs plus a **durable barrier before any external negative wallet adjustment**. Do not fix B5 by permitting consumer debt, discarding a served event, or granting free credits to hide it.

1. Normal background refresh installs `{walletId,ownerKey,epoch,balance,sequence,gateRevision,validUntil,lots,keyPolicies}`. One DO owns that epoch; no overlapping regional grant. Within an epoch, edge available equals authoritative balance minus active holds and finalized-but-unacknowledged debits. A higher checkpoint sequence must not add those amounts back; reconcile accepted refs and checkpoint atomically, preserving local holds. A grant/checkpoint never resets key-family month totals or free-tier counters. Admission durably records `reservationId,epoch,edgeSequence,maxCredits,fundingSlices,immutable spec/pricing identity,keyFamily/budget evidence,admittedAt` before upstream. A server-authenticated admission fingerprint binds those facts. Free calls also get a durable admission/finalization record.
2. A refund, dispute withdrawal, expiry, org archive or negative adjustment records its canonical source fact and sets `gateState=closing` and a unique `close.id`. It **does not debit balance yet**. An async control action requests the existing wallet DO to freeze; background pulls also see closing. Push is a wake-up/control optimization, not a registry outbox or per-request Convex dependency.
3. DO persists the close ID, stops new admissions, finishes/refunds active holds, and flushes pending finalizations from that epoch. Already-dispatched requests remain source-backed because Convex has not reclaimed their credits. It seals the epoch and reports `edgeFinalSequence` after every reservation has a final outcome. Crash recovery resumes this state from SQLite; a timeout cannot invent a successful drain.
4. Convex accepts valid previously admitted settlements while closing, including after org archive or route retirement. Check immutable version/publisher/admission facts, **not today's mutable publication/visibility policy**. Verify a contiguous finalization watermark through `edgeFinalSequence`; lost acknowledgements replay unchanged refs. A caller cannot make a new admission by replaying an old route revision.
5. Once all finals are committed, Convex applies reversal/expiry only to remaining inventory; payment expenditure becomes publisher clawback exposure. It appends exact wallet entries, advances the epoch, then reopens the remaining legitimate balance (or stays closed for archive). DO installs this epoch only after sealing the prior one; stale checkpoints cannot resurrect spendable credit.
6. If DO is unreachable, the adjustment remains pending and the wallet fails closed when its current authority expires. Recovery must obtain the durable final journal before reclaiming funds; expiry of a lease is **not proof** that a dispatched call did not run. Operator intervention may resolve a lost DO, but cannot guess usage or erase the open case.

This trades short adjustment latency for no unmetered execution and no consumer overdraft. A Stripe dispute may debit the platform before wallet closure completes; record that external fact immediately and treat the bounded delay as platform exposure, never fictitious consumer debt. Proposed authority freshness is 30 seconds; owner must accept that stale-admission window and wallet closure availability cost. Existing max execution/stream deadlines bound active hold drain; LLM streams need an explicit maximum lifetime before activation.

Settlement v2 adds `protocolVersion:2,walletId,ownerKey,epoch,edgeSequence,admittedAt,admissionFingerprint,heldCredits,fundingSlices` plus immutable token/capability evidence when applicable. HMAC or an equivalent authenticated Worker attestation uses a dedicated signing key and binds environment/deployment, wallet, request, price and reservation; reusing a proof with changed immutable facts is a terminal conflict. It is not proof that a compromised Worker reported truthfully: the Worker is inside the accounting trust boundary. Keep batch outcomes and checkpoint envelope recognizable, and extend checkpoint with epoch/gate state. Invalid evidence is retained in a durable operational failure record on the DO; never acknowledged as a completed financial event.

### Top-ups, signup, and expiry

- Paid Checkout: server creates `checkoutIntent` and durable provider idempotency keys; verifies canonical session, paid status, currency, customer, intent, price IDs, quantities and total before granting. Principal credits and fee line are distinct. Browser success/return URLs grant nothing.
- `$1` signup: webhook and authenticated ensure-org both call one transactionally idempotent grant function. Grant only after the chosen eligibility rule is met. An archived/recreated Clerk ID cannot regrant. Zevium funds the publisher's 95% when promo credits are spent; promo is nonrefundable and receives no special settlement discount.
- x402: only successful verified settlement funds a lot. Session/challenge replay cannot create another grant; unique provider payment reference is stronger than HTTP event ID. Later calls use the same DO/ledger and split as org calls, with no on-chain operation per call. Finality/facilitator policy belongs to #109, not this rebuild's implementation scope.
- Expiry: DO cannot reserve an expired lot even if the cron is late. A scheduled freeze/drain expires remaining inventory by lot, preserving already admitted holds. Top-up B never extends top-up A. Expiry entries have deterministic lot/expiry refs. Restored credits keep the original deadline. Breakage accounting and notices remain owner policy.
- Fees: persist quoted fee, charged fee, eventual actual provider fee and variance. Validate fee-policy version/quote lifetime. Never mint credits for processing fees. Do not assume a universal rate or “at-cost” accuracy before payment method, region and final provider fee are known. Keep passthrough activation disabled until quote/reconciliation/refund policy can satisfy the accepted decision.

### Publisher earnings, transfers, refunds and disputes

`publisherEarnings` is a sharded daily **payment-specific** bucket, not a per-call row. The earning bucket day is the server acceptance date, so late-arriving usage cannot append to a day already released; usage analytics still use validated execution time. Count calls in usage rollups once per settlement, never by summing source-slice contributions. Use a deterministic shard from settlement ref (proposed 16); sum split atoms from accepted calls rather than recomputing from rounded daily credits. `availableAt = UTC end-of-day + seven days` avoids releasing late-added calls early, at the cost of up to 24 hours extra hold; owner may choose hourly buckets if exact seven-day release is required. Release each earning bucket in its own mutation and schedule bounded independent work; one corrupt publisher cannot stop the global batch (B10). `publisherBalances` changes on release, clawback and transfer, never on every call.

Transfer preparation atomically moves whole-cent atoms from available to allocated and creates `publisher-transfer:<org>:<transferSequence+1>`. Leave sub-cent remainder in available. Re-fetch the v2 recipient capability before dispatch; require active transfer capability and verified environment/account/destination. Persist the exact request fingerprint and random server operation nonce before calling Stripe. Provider metadata is correlation, not authorization: canonical provider amount, currency, destination, mode, account and nonce must all match before adopting a result. One connected account can belong to only one org through an indexed transactional claim on `organizations.connect.accountId`.

Keep these distinct transfer states:

- **Definitive no-side-effect failure:** record failure and release allocation once. A later admin retry creates a new attempt/transfer with a new idempotency key after funding/capability correction; it does not loop forever on a cached error (B9).
- **Unknown outcome after dispatch:** retain allocation and reconcile the original request; retry the same exact request only within the provider's verified safe replay window. When that window is over, do not create again merely because a bounded scan found nothing. Page provider reconciliation with a durable cursor and surface `needs_review`; no 100-account hard failure (B14).
- **Verified success / cumulative reversal:** append only the delta not already applied. Bank payout projection is separate from transfer accounting and never causes a second wallet or earnings debit.

Stripe API v1 caches the initial executed request's result, including errors, and idempotency retention is finite; Accounts v2 retry semantics differ. Do not share one retry policy between v1 transfers and v2 account creation. [Stripe idempotency documentation](https://docs.stripe.com/api/idempotent_requests).

Refund/dispute processing:

1. Receive raw-body verified event; dedupe receipt plus schedule processor in one mutation. Claim with a lease token; fetch canonical provider objects in an action. Completion rejects stale tokens. Recovery queries both due retries and abandoned leases. Keep the three separate Stripe destinations; thin notifications and snapshot events have different payload contracts. [Stripe webhook documentation](https://docs.stripe.com/webhooks).
2. Upsert one source adjustment per refund/dispute. Pending and `requires_action` refunds reserve exposure; failed/canceled refunds restore it. Dispute lifecycle `created`/`closed` does not move money; only verified withdrawal/reinstatement facts do. Persist event movement facts separately from a current status so replay order cannot invent a withdrawal.
3. Compute combined active reversal target capped by original credited principal. A processing-fee refund never subtracts credits twice. Freeze/drain affected wallet before reclaiming remaining lot inventory, then attribute the remainder to **that payment's consumed credits**, never another payment or promotional lot.
4. Walk `publisherEarnings.by_payment` in bounded pages. Apply deterministic `(adjustment generation,earning bucket)` journal refs; save cursor and generation in the same mutation as effects. A stale job cannot apply a superseded target. Unreleased earnings shrink their releasable amount; already released/paid earnings claw back available balance, which may go negative and blocks further transfers. Reverse the platform's original fee share proportionately as an explicit journal fact.
5. On reinstatement, reverse the exact applied journals before restoring wallet inventory. Never allocate restoration by today's FIFO order or credit more than was removed. Overlapping partial refunds/disputes need deterministic source ordering and cap attribution; once a target is capped, source-specific applied amounts preserve which reversal is being undone.
6. Keep canonical adjustment/reconciliation state until complete. A table called `publisherClawbacks` or `publisherReconciliationJobs` is unnecessary when journals plus payment cursor/generation carry the same evidence; deleting the evidence itself is not permitted.

House listings enter the same immutable usage path and carry actual upstream cost metadata when available; the flag does not assume a special house 95/5 accounting policy. No LLM house listings per the accepted direction.

### LLM hold/settle and capability attempts

Spec-declared input/output rates and maximum are immutable pricing inputs. Estimate input plus permitted output (`max_tokens`, else declared cap), enforce per-call maximum and DO in-flight budget, reserve before upstream, then settle actual measured tokens and release the unused hold. Store `heldCredits`, token counts, rate units, actual atoms, integer-credit rounding and final usage source. Require `0 <= actualCredits <= heldCredits`; over-limit output stops under a defined adapter rule, never surprise-overages. Direct response remains streaming; a bounded observer reads terminal usage without unbounded tee buffering. MCP's 1 MiB preparation and refund-before-finalization behavior from #381 survives.

Missing/invalid usage is unresolved product policy. Proposed default is refund and record a failed/ambiguous usage outcome, with no publisher earning, until an approved reconciliation policy exists; **do not silently charge the estimate**. Token execution remains disabled until that choice and extension shape are approved and tested. Schema support can ship earlier.

Capability attempts link by `routeRequestId` with unique reservation/settlement refs per attempt. Validate normalized successful result before settling, and preserve the actual provider/publisher identity. Failed attempt refund does not erase its usage or quality sample. The proposed gross-attempt max-cost rule, two-attempt bound, mapping grammar and taxonomy remain owned by the capability design; the schema can represent them without approving them.

### Replace registry outbox with signed pull snapshots

**Decision proposed here:** no route/key/catalogue event outbox and no new registry v2 receiver. The baseline still contains the v1 registry/ControlDO branch; #376 removes it, and no working v2 receiver exists. Gateway currently pulls Convex data on cache misses; the replacement uses a background edge refresh service and short-lived signed projections. Merely renaming `/gateway-spec` does not meet the no-network hot-path rule.

- Add gateway-authenticated `GET /edge-snapshot?kind=org|route|keys|catalogue|capability&scope=...&cursor=...`. A response envelope includes `schemaVersion,deploymentId,kind,scope,revision,generatedAt,expiresAt,keyId,payloadDigest,payload,nextCursor?` and a signature over canonical bytes plus request nonce. Use a dedicated signing key/key ID and verifier rotation overlap; constant-time MAC check or audited signature verification. Request authentication and publisher credential encryption have different keys.
- Organization/key scopes use org/key revisions; route uses project/publication and credential revisions; catalogue/capability snapshots refer to exact route/spec digests. A route response joins live org, reservation, project and spec **in one query**. Page manifests are immutable for their generation; generate/hold them in private edge snapshot storage (R2/cache coordinator), not by walking changing current rows with an unpinned cursor. Abort/restart a generation whose source revision changes while building. PR 5 must prove page consistency under concurrent publish/revoke.
- A scheduled edge refresh worker/coordinator pulls and verifies scopes, installs complete generations atomically, and distributes them to edge-readable storage. A request reads that edge state plus its wallet DO only. Missing or expired authority returns unavailable and schedules refresh; it does not synchronously call Convex or Clerk. Public discovery may serve a bounded older public catalogue only after filtering current org/route kill state; execution always requires fresh authority.
- No deployment-wide revision document touched per call or mutation. Track scope revisions and refresh known scopes on a timer; new publishes/key registrations request a best-effort wake-up. Polling is limited to the separate edge replication boundary, not dashboard queries: web remains Convex realtime. Proposed refresh interval 15s, executable authority lifetime 30s; catalogue display lifetime 60s. These are measurable availability/security tradeoffs, not claims about current code.
- Revocation and org archive are terminal monotonic revisions. Combine every key/route/capability read with current org authority; lower revisions, replayed nonce, wrong deployment, expired envelope and signature mismatch fail closed. A lost wake-up is recovered by refresh; acknowledge local revocation immediately but expose maximum edge propagation delay rather than promising instant global revocation. For stronger guarantees, add acknowledged edge revocation before declaring completion; owner must choose before launch.
- Unknown key hashes never authorize. Broker-verified rows carry Clerk identity/owner/subject, independent budget ID and secret hash, so the gateway verifies possession against a fresh projection without per-call Clerk verification. Raw API keys never enter Convex. Existing `registerVerified` HMAC assertion remains an issuance boundary, separate from snapshot signatures.
- Public snapshot contains no publisher headers, key hashes or private listing state. Private route headers use a current AES-GCM transport envelope bound to route revision/environment, decrypted only at the executing Worker. No raw credentials in shared Cache API entries, public logs, persistent plaintext edge storage, or catalogue snapshot.
- `/wallet-grants` remains the authoritative reconciliation transport, including key caps, epoch and funding inventory; it is not a global route registry. Freeze/drain requests are a separate authenticated control operation backed by wallet state and recovery, not best-effort cache invalidation.

## 6. Risks and owner questions

**Resolve before committing PR 1's contracts:**

1. **Accept the availability and size tradeoffs?** Recommended: 32 application tables, 30-second executable snapshot authority, freeze/drain before negative wallet adjustments, and no consumer debt. A lost/unreachable DO can delay refunds and temporarily close that wallet. Is that acceptable, or is stronger immediate global revocation worth an acknowledged control path? Also confirm a 32-funding-slice admission bound or require a resumable allocator.
2. **Who qualifies for the $1 grant?** Amount and once-per-org behavior are decided; verified eligibility and anti-farming limits are not. Specify the server-verifiable signal and whether an admin's multiple orgs all qualify. Anonymous sessions currently receive no grant.
3. **What are the unresolved money policies?** Confirm processing-fee quote/true-up and refund treatment, missing/invalid LLM usage behavior, and whether daily buckets may delay seven-day risk release by up to 24 hours. Proposed safe defaults keep card surcharge/token execution disabled until approved and preserve ordinary fixed-price paid calls.

Further open questions remain with their existing owners:

- x402 settlement provider/finality, accepted network/address normalization, session authentication lifetime, expiry notices and accounting treatment of one-year breakage (#109; [machine-payments](../features/machine-payments.md)). Session TTL and lot TTL are separate decisions.
- Capability governance, mappings, supplier pair and gross-attempt cap remain proposed in [capability routing](../design/capability-routing.md); the schema should not turn a merged design into approval.
- House supply rights/subsidy cap and internal 95/5 accounting are unresolved. Preserve house flag and cost facts without clearing these launch gates.
- Source-specific buckets can still multiply with many payments/publishers. Measure hot publisher sharding and refund scan completion with many sources; keep the per-call publisher balance write forbidden. Component rate limiting has its own contention/storage cost.
- Exact whole-credit LLM rounding versus fractional-credit wallets needs an approved rule. Proposed launch uses ceil-to-credit actual charge bounded by hold, records rounding atoms, and discloses it; rates must not create hidden markups.
- A pinned multi-page snapshot is extra edge infrastructure. Specify coordinator failure/recovery, encryption at rest, clock skew and deployment signing-key rotation in PR 5; do not claim a TTL wrapper on live queries is equivalent.
- Payment provider side effects survive disposable database resets. Separate sandbox environments and persist cleanup/reconciliation identifiers; production cutover cannot strand unknown transfers or process the same payment in both deployments.
