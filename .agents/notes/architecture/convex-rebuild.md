# Convex control-plane rebuild

> Status: PR 1 reviewed foundation and isolated PR 2 identity/publishing implemented, including all six PR #437 review fixes; isolated PR 3 wallet lots and source-backed settlement implemented for [#353](https://github.com/zevium-dev/core/issues/353). Updated: 2026-10-11. Surcharge activation remains gated by #318; deferred features are outside this stack.
> PR 1 baseline: `84f12c45` on `origin/develop` (2026-10-11), including plan PR #394. Owner decision PR #433 was read while open and is now merged. The historical 81-function table below remains context; the machine-checked inventory in `packages/control-plane-next/contracts/inventory.json` owns current coverage. Existing code is evidence of current behavior, not approval to carry deferred features into the replacement. Fresh isolated local deployments; no customer-data migration or live schema changes.

Build a replacement behind the existing web function names, then switch web, gateway, and provider destinations to one fresh deployment. Preserve the accounting and authorization contracts, replace funding lineage with lots and indexed original-source balances, and remove the unused registry outbox after moving its two live responsibilities. Use seven implementation PRs, with independent feature and wallet work after the foundation.

The [audit](../findings/codebase-audit-convex.md) is the starting point, not a current inventory. The target is **35 application tables: 9 identity/publishing + 8 wallet/payment + 6 settlement/analytics + 12 read/background**. Starting from the previous 32, remove `walletSessions` and `capabilityProviders`, then add `fundingLotSources` so dust merges preserve indexed payment provenance without unbounded arrays. Token pricing had no dedicated table; removing its fields does not reduce the physical count. The audit's approximate 24 grouped multiple physical tables together. Preserve three independent durable facts with `notificationPreferences`, `notificationEmailDeliveries`, and `financeReconciliationCases`; user authorization on 2026-10-11 raises the table budget rather than dropping baseline behavior. Preferences are not user-global, enqueue receipts outlive provider cleanup, and unowned/quarantined provider facts cannot safely be ledger rows. Reconciliation evidence uses indexed child rows in the same table, never unbounded arrays. PR 2 review adds `projectDrafts` as the 35th app table: draft text can approach 393 KB, so it must not inflate project list/archive/sunset reads; projects retain only small draft metadata and readiness. Component-owned rate-limiter tables are additional; PR 1 reports their actual count separately.

The publisher's immutable OpenAPI spec is the contract: gateway routes, catalogue, docs, mocks and agent surfaces are generated from it. One listing has one upstream. This stack supports scalar per-call pricing, org wallets and Stripe top-ups; token execution, capability routing and x402 settlement are deferred. The owner-answer decision records for snapshot authority, dust merging, signup eligibility, fee/refund policy and deferred features are being written separately for 2026-10-11; this plan incorporates those answers without creating duplicate records.

## 1. Current surface contract

Inventory method: read `convex/schema.ts`, `http.ts`, registered exports in every current module, and direct `api.module.function` plus string `makeFunctionReference` callers in `apps/web/src` and `apps/gateway/src`; exclude tests and incidental URLs. **81 distinct function names** below in that original inventory; this is a historical fixture seed, not a verified count for the rebased tree. PR 1 enumerates current exports/callers and records retained, changed and intentionally retired contracts before freezing fixtures. Gateway also called three HTTP routes. The old deployed-key `wallets:recordUsage` fallback has since been removed; do not restore it. Provider routes and now-unused release tooling APIs are listed separately.

Notation: `?` means optional; `Id<T>` is the generated Convex ID type, not an arbitrary client-selected tenant. `paginationOptsValidator` means `{numItems,cursor:string|null}` plus Convex's optional pagination controls. `Page<T>` means `{page:T[],isDone,continueCursor}` with optional framework split/status fields preserved. The source validators still own exact bounds and error behavior. `orgSlug` is a navigation consistency check; authorization derives the active org from the signed JWT.

DTO abbreviations:

- `Project`, `Organization`, `User`, `Review`, `SpecVersion`, and `RotationOperation` currently expose source documents. Preserve consumed fields; replace document returns with explicit DTOs before embedding secrets in a target row. Never spread target `projects` or `organizations` into a response.
- `KeySettingView`: `_id,keyId,keyFamilyId,keyName?,ownerUserId?,budgetId?,budgetRevision?,monthlyCapCredits?,disabled,rotatedFromKeyId?,graceUntil?,rotationRequiredAt?,lifecycle?,createdAt,updatedAt`. No raw key or hash. Boundary validators are `verifiedKeyProjectionValidator` / `verifiedKeyRotationProjectionValidator` in `convex/keySettings.ts`, with shared signature/semantic verification; keep their full signatures and expiry/identity checks.
- `PublicListing`: listing name/slug/description/tags, publisher name/handle, publication time, pricing/free-tier summary, endpoint count, quality. `PublicReview`: `id,rating,body,createdAt,updatedAt,reviewerLabel,response:{body,updatedAt}|null`.
- `UsageListItem`: `eventId,projectRef,projectName,projectSlug,endpoint,method,credits,status,latencyMs,keyId,memberId?,memberName?,at`. Preserve member redaction from `usageView`.
- `WebhookEndpointMetadata`: `url,active,secretVersion,createdAt`. `OrgAccess` is the shared role/capability DTO. `getPayoutState` totals retain pending/available/allocated/paid/reversed/failed values; aggregation must not change with the recent-rows limit.

## 2. Target schema

All rows get Convex `_id` and `_creationTime`. Unless marked `?`, fields are required. Times are UTC epoch milliseconds; `day` is UTC date and money uses safe integers. An optional field exists only for a product state (not a migration stage). Discriminated unions require their variant's fields. Enumerated state names below are implementation proposals, with validators frozen in PR 1.

Index notation `name(fields) → query` specifies both ordering and the named consumer. “Unique” means an indexed absence/read check and write in the **same mutation**; a Convex index does not impose a SQL uniqueness constraint. Scope every ID lookup with authenticated ownership before returning it. [Convex index documentation](https://docs.convex.dev/database/reading-data/indexes/) describes range ordering; test concurrent insertion rather than assuming `.unique()` enforces uniqueness.

## 3. Money core: small transactions, explicit edge authority

### Size and module boundary

Target **~2,200 non-test lines for ledger/lot/settlement policy**, excluding Stripe HTTP, crypto, tenancy, DTOs and recovery transport. Allocation: `money/walletLedger.ts` 180, `money/lots.ts` 500, `money/settle.ts` 340, `money/adjustments.ts` 500, `money/publisherLedger.ts` 260, `money/transfers.ts` 240, `accounting.ts` 100, shared types 80; total **2,200**. Relative to the previous 2,000-line target, removing token/capability settlement saves about 80 lines, bounded dust moves/source balances add about 200, and source-aware reversal/restoration adds about 80. These are planning estimates to measure in PR 4, not a code cap. Stripe orchestration stays in `billing.ts`, `payouts.ts` and small provider actions; each DB mutation completes one bounded state transition.

There is one serialized edge wallet per `ownerKey` and one authoritative Convex ledger per wallet. Per-request admission stays in the wallet DO. Convex batches wallet writes; the mandated sharded rate-limiter component protects contended admission to paid search/import/report actions, **not** the money ledger. Neither a rate limiter nor eventual aggregation can replace atomic ledger accounting. Update dashboard/earnings rollup deltas in the accepted settlement transaction, once per ref; release/reversal transactions also update their financial rollup deltas. Background recomputation is a bounded audit, not a second eventually consistent money source.

### Wallet invariant and funding lots

For every committed wallet transaction:

1. `balance = sum(walletEntries.amount) >= 0`; `sequence` is contiguous and each entry's `balanceAfter` is exact. Only `appendWalletEntry` changes balance. Same ref + identical immutable facts is a no-op; same ref + changed facts fails before any write.
2. `balance = sum(lot.remainingCredits)` and each lot satisfies `granted + movedIn = remaining + consumed + reversed + expired + movedOut`. Each source-balance row satisfies `creditsIn = remaining + consumed + reversed + expired + creditsOut`; summed source rows equal their container totals. Restoration moves reversed credits back to remaining at the exact recorded container/source, preserving the original payment identity and expiry; it never borrows the destination lot's payment identity. Restore to expired inventory if its original expiry has passed.
3. `promoCredits` equals remaining nonrefundable promotional inventory. Consume promo first, then refundable containers FIFO by creation time and ID, with source rows ordered by original creation time and ID within a container. Dust moves deliberately move the remainder to the newest compatible container without changing its original source. Positive admin credits also have explicit lots; negative adjustment uses the same allocator and freeze protocol. Its canonical applied fact is the immutable per-source `walletEntries` reversal set, grouped by wallet and server-issued `adjustment:{kind:"admin",ref}` and indexed by `by_admin_adjustment`; no fake payment/paymentAdjustment row. PR 3 must apply the bounded source set atomically after drain, give entries deterministic per-source refs and a request fingerprint, reject changed-fact replay, and restore only those recorded sources. Pending drain state stays on `wallets.close`; a rejected/unapplied command has no ledger fact.
4. Every settled debit has exact source slices and a usage row; every paid source slice yields exact `publisherEarningSplit`. Zero balance denies even explicit-zero-price/free-tier execution; keyless mock remains the stated non-executing exception.
5. All money/sequence inputs are bounded safe integers. Credits use 10,000 per USD; accounting atoms use 10,000 per credit. No floating-point dollars in a ledger mutation.

The v2 background checkpoint carries available containers and original-source balances, priorities and expiry times into the single DO. Checkpoints are paged at a pinned wallet sequence and installed atomically. Admission durably reserves at most **32 original-source slices**, including provenance inside merged lots, before dispatch. A request needing more slices fails before upstream with a recoverable funding-capacity error. The owner accepted this bound; **no resumable admission allocator** is in scope. **Owner clarification:** the 32-slice cap counts original payment sources, including ones inside merged lots. Dust merging reduces lot count, not slice count; this is acceptable for org wallets and does not guarantee every funded request fits the bound.

#### Dust merging with payment provenance

Use **1,000 credits ($0.10)** as the initial configurable dust threshold: merge only when `0 < remainingCredits < 1_000`. Choose the newest other eligible lot in the same wallet, ordered by `(createdAt, _id)`, and only a strictly newer destination to prevent cycles. Compatibility requires **identical expiry rules and exact `expiresAt`** (including both absent), plus the same source kind, refundability and spend priority. Equal one-year durations with different deadlines are not compatible. Without a compatible destination, leave the dust in place. Promo never merges into a paid lot.

Run merges as background maintenance under the same durable freeze/drain barrier as adjustments. Drain old holds/finalizations before changing funding inventory; resume admission only on the new epoch checkpoint. Pin the destination and merge generation on the source lot. Process at most 32 source rows per transaction with a persisted cursor; each transaction appends one deterministic `lot_move` entry per original source and atomically updates both containers and `fundingLotSources` balances. A move records from lot, to lot, original source/payment, amount and reason; its wallet delta is zero. Retries with the same ref/facts are no-ops. Crash recovery resumes the stored job, and repeated merges retain direct original-source indexes rather than traversing a growing chain. Serialize merge and reversal jobs for that wallet.

Settlement records both the container and original source in each slice. Earnings always use the **original payment/source**, even when the destination lot was created by a different payment. Refunds/chargebacks query `fundingLotSources.by_payment` in bounded pages to reclaim that payment's remaining money wherever it moved, then reverse its consumed earning buckets. Other payments' balances and earnings remain untouched. Retain move/source rows needed by unsettled adjustments; never compact provenance into an unbounded document array.

Convex validates slices against the locked wallet epoch, then atomically appends the debit, updates container/source balances, inserts immutable usage and increments sharded original-source earning buckets. Budget the **one-event worst case at 32 slices**, including all source rows and earnings/rollup writes, before grouping events within the measured transaction write/byte limit; retain the 100-event wire cap. A large batch may return retryable unprocessed refs, but one valid admitted event always fits and progresses. Background merge/reversal cursors do not turn admission into a resumable allocator. The new source-balance table and explicit move journal replace the old funding-state/allocation mirrors.

### Fix #357 with a freeze/drain barrier

A newer balance alone is not enough to reconcile two authorities. Accepted v2 contract: epochs plus a **durable barrier before any external negative wallet adjustment**. Do not fix B5 by permitting consumer debt, discarding a served event, or granting free credits to hide it.

1. Normal background refresh installs `{walletId,ownerKey,epoch,balance,sequence,gateRevision,validUntil,lots,keyPolicies}`. One DO owns that epoch; no overlapping regional grant. Within an epoch, edge available equals authoritative balance minus active holds and finalized-but-unacknowledged debits. A higher checkpoint sequence must not add those amounts back; reconcile accepted refs and checkpoint atomically, preserving local holds. A grant/checkpoint never resets key-family month totals or free-tier counters. Admission durably records `reservationId,epoch,edgeSequence,maxCredits,fundingSlices,immutable spec/pricing identity,keyFamily/budget evidence,admittedAt` before upstream. A server-authenticated admission fingerprint binds those facts. Free calls also get a durable admission/finalization record.
2. A refund, dispute withdrawal, expiry, org archive or negative adjustment records its canonical source fact and sets `gateState=closing` and a unique `close.id`. It **does not debit balance yet**. An async control action requests the existing wallet DO to freeze; background pulls also see closing. Push is a wake-up/control optimization, not a registry outbox or per-request Convex dependency.
3. DO persists the close ID, stops new admissions, finishes/refunds active holds, and flushes pending finalizations from that epoch. Already-dispatched requests remain source-backed because Convex has not reclaimed their credits. It seals the epoch and reports `edgeFinalSequence` after every reservation has a final outcome. Crash recovery resumes this state from SQLite; a timeout cannot invent a successful drain.
4. Convex accepts valid previously admitted settlements while closing, including after org archive or route retirement. Check immutable version/publisher/admission facts, **not today's mutable publication/visibility policy**. Verify a contiguous finalization watermark through `edgeFinalSequence`; lost acknowledgements replay unchanged refs. A caller cannot make a new admission by replaying an old route revision.
5. Once all finals are committed, Convex applies reversal/expiry only to remaining inventory; payment expenditure becomes publisher clawback exposure. It appends exact wallet entries, advances the epoch, then reopens the remaining legitimate balance (or stays closed for archive). DO installs this epoch only after sealing the prior one; stale checkpoints cannot resurrect spendable credit.
6. If DO is unreachable, the adjustment remains pending and the wallet fails closed when its current authority expires. Recovery must obtain the durable final journal before reclaiming funds; expiry of a lease is **not proof** that a dispatched call did not run. Operator intervention may resolve a lost DO, but cannot guess usage or erase the open case.

This trades short adjustment latency for no unmetered execution and no consumer overdraft. A Stripe dispute may debit the platform before wallet closure completes; record that external fact immediately and treat the bounded delay as platform exposure, never fictitious consumer debt. The owner accepted **30-second executable authority through the wallet DO**, the stale-admission window and the possibility that a lost/unreachable DO delays refunds or keeps a wallet closed. There is no global revoke path. Existing execution/stream deadlines bound active hold drain; lease expiry alone never proves a drain.

Settlement v2 adds `protocolVersion:2,walletId,ownerKey,epoch,edgeSequence,admittedAt,admissionFingerprint,heldCredits,fundingSlices`; funding slices bind original source as well as container. HMAC or an equivalent authenticated Worker attestation uses a dedicated signing key and binds environment/deployment, wallet, request, price and reservation; reusing a proof with changed immutable facts is a terminal conflict. It is not proof that a compromised Worker reported truthfully: the Worker is inside the accounting trust boundary. Keep batch outcomes and checkpoint envelope recognizable, and extend checkpoint with epoch/gate state. Invalid evidence is retained in a durable operational failure record on the DO; never acknowledged as a completed financial event.

### Top-ups, signup, and expiry

- Paid Checkout: server creates `checkoutIntent` and durable provider idempotency keys; verifies canonical session, paid status, currency, customer, intent, price IDs, quantities and total before granting. Principal credits and fee line are distinct. Browser success/return URLs grant nothing.
- `$1` signup: signed organization creation establishes the first processed creator binding. In that transaction, claim `users.signupGrant` atomically with the 10,000-credit lot/source and wallet entry. Existing claims remain consumed. Joining, organization updates, client metadata and anonymous wallets receive nothing; ensure calls cannot nominate a recipient. An archived org or deleted/recreated user mirror cannot regrant. Zevium funds the publisher's 95% when promo credits are spent.
- x402 is disabled and omitted from the replacement. Keep only the schema seams described in section 2; no settlement, session or anonymous top-up work in the seven PRs.
- Expiry: org lots do not expire. The generic lot invariant preserves exact deadlines for future expiring lots; any expiry uses freeze/drain and deterministic lot/source refs, with remaining breakage recorded as **Zevium revenue**, never publisher earnings. Restore reversed inventory to expired inventory if its original deadline has passed. No expiry display or warning notifications are in scope.
- Fees: show an estimated processing-fee line at Checkout, retain the charged amount as the customer's final amount and let **Zevium absorb variance, with no true-up**. Actual fee/variance are internal accounting facts. Never mint credits for the fee line. Surcharge collection remains disabled pending legal #318; zero-fee Checkout still works. A full refund returns **exactly `amountPaidCents`**, including the charged fee line; Zevium bears the Stripe processing fee. Partial refunds carry separately recorded principal/fee cents, with cumulative refunds capped at the amount paid and the final refund returning every remaining cent. Only principal reverses credits. [Stripe refund documentation](https://docs.stripe.com/refunds) confirms original processing fees are not returned.

### Publisher earnings, transfers, refunds and disputes

`publisherEarnings` is a sharded daily **payment-specific** bucket, not a per-call row. The earning bucket day is the server acceptance date, so late-arriving usage cannot append to a day already released; usage analytics still use validated execution time. Count calls in usage rollups once per settlement, never by summing source-slice contributions. Use a deterministic shard from settlement ref (proposed 16); sum split atoms from accepted calls rather than recomputing from rounded daily credits. `availableAt = UTC end-of-day + seven days` avoids releasing late-added calls early, at the cost of up to 24 hours extra hold; the owner accepted this daily-bucket delay, so hourly buckets are out of scope. Release each earning bucket in its own mutation and schedule bounded independent work; one corrupt publisher cannot stop the global batch (B10). `publisherBalances` changes on release, clawback and transfer, never on every call.

Transfer preparation atomically moves whole-cent atoms from available to allocated and creates `publisher-transfer:<org>:<transferSequence+1>`. Leave sub-cent remainder in available. Re-fetch the v2 recipient capability before dispatch; require active transfer capability and verified environment/account/destination. Persist the exact request fingerprint and random server operation nonce before calling Stripe. Provider metadata is correlation, not authorization: canonical provider amount, currency, destination, mode, account and nonce must all match before adopting a result. One connected account can belong to only one org through an indexed transactional claim on `organizations.connect.accountId`.

Keep these distinct transfer states:

- **Definitive no-side-effect failure:** record failure and release allocation once. A later admin retry creates a new attempt/transfer with a new idempotency key after funding/capability correction; it does not loop forever on a cached error (B9).
- **Unknown outcome after dispatch:** retain allocation and reconcile the original request; retry the same exact request only within the provider's verified safe replay window. When that window is over, do not create again merely because a bounded scan found nothing. Page provider reconciliation with a durable cursor and surface `needs_review`; no 100-account hard failure (B14).
- **Verified success / cumulative reversal:** append only the delta not already applied. Bank payout projection is separate from transfer accounting and never causes a second wallet or earnings debit.

Stripe API v1 caches the initial executed request's result, including errors, and idempotency retention is finite; Accounts v2 retry semantics differ. Do not share one retry policy between v1 transfers and v2 account creation. [Stripe idempotency documentation](https://docs.stripe.com/api/idempotent_requests).

Refund/dispute processing:

1. Receive raw-body verified event; dedupe receipt plus schedule processor in one mutation. Claim with a lease token; fetch canonical provider objects in an action. Completion rejects stale tokens. Recovery queries both due retries and abandoned leases. Keep the three separate Stripe destinations; thin notifications and snapshot events have different payload contracts. [Stripe webhook documentation](https://docs.stripe.com/webhooks).
2. Upsert one source adjustment per refund/dispute. Pending and `requires_action` refunds reserve exposure; failed/canceled refunds restore it. Dispute lifecycle `created`/`closed` does not move money; only verified withdrawal/reinstatement facts do. Persist event movement facts separately from a current status so replay order cannot invent a withdrawal.
3. Compute combined active reversal target capped by original credited principal. A processing-fee refund never subtracts credits twice. Freeze/drain affected wallet before reclaiming remaining original-source inventory across merged containers via `fundingLotSources.by_payment`, then attribute the remainder to **that payment's consumed credits**, never another payment or promotional lot.
4. Walk `publisherEarnings.by_payment` in bounded pages. Apply deterministic `(adjustment generation,earning bucket)` journal refs; save cursor and generation in the same mutation as effects. A stale job cannot apply a superseded target. Unreleased earnings shrink their releasable amount; already released/paid earnings claw back available balance, which may go negative and blocks further transfers. Reverse the platform's original fee share proportionately as an explicit journal fact.
5. On reinstatement, reverse the exact applied journals before restoring wallet inventory. Never allocate restoration by today's FIFO order or credit more than was removed. Overlapping partial refunds/disputes need deterministic source ordering and cap attribution; once a target is capped, source-specific applied amounts preserve which reversal is being undone.
6. Keep canonical adjustment/reconciliation state until complete. A table called `publisherClawbacks` or `publisherReconciliationJobs` is unnecessary when journals plus payment cursor/generation carry the same evidence; deleting the evidence itself is not permitted.

House listings belong to an ordinary Zevium publisher organization and receive the same 95/5 split, risk release, reversals and transfers as every publisher. No house accounting tables or special settlement branches. Omit the optional $100/month subsidy cap from this stack; it can be added later if existing spend controls make it trivial.

### Deferred execution models

LLM per-token execution is entirely outside this rebuild: no token-pricing tables/fields, usage observers or actual-token settlement. Future owner direction is a fixed ~$0.10 hold, an approximately -$1 balance floor with new calls blocked at/below zero, upstream cancellation on disconnect and finer credit granularity. Allowing a call to settle below zero conflicts with the current no-surprise-overage/no-consumer-debt rule and requires an explicit amendment before revival. Keep fixed-price holds and MCP's 1 MiB buffering/refund-before-finalization contract.

Capability routing is also deferred: one listing = one upstream, with surfaces generated from the publisher's OpenAPI spec. No membership, routing-attempt, mapping or normalized-contract fields ship in this schema. Future governance and supplier selection belong to the separate [capability design](../design/capability-routing.md), not a PR 1 blocker.
